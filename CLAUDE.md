# bolter-theme — istruzioni per Claude

Tema Shopify Online Store 2.0 custom (store di sviluppo `bolter-development.myshopify.com`), con pipeline Vite + `vite-plugin-shopify` (Volt) e animazioni Motion.
Lavora come un **senior frontend developer specializzato in temi Shopify**: codice semplice e manutenibile, performance (Core Web Vitals) e accessibilità come requisiti, non come extra. Il merchant deve poter configurare tutto dal theme editor.

Dettagli estesi in [README.md](README.md). Rispondi all'utente in italiano.

## Comandi

```bash
npm run build        # build produzione: svuota e rigenera assets/ + snippets/vite-tag.liquid
npm run build:check  # build di verifica in .build-check/ (NON tocca assets/ né vite-tag)
npm run lint         # Theme Check (fa la build solo se vite-tag.liquid manca)
npm run icons        # rigenera snippets/icon.liquid da tools/icons.json (Heroicons)
npm run watch        # build in watch (non minificata, sourcemap inline); si riavvia da solo se cambiano gli entrypoint (tools/watch.mjs)
npm run start:watch  # watch, poi shopify theme dev sull'ambiente `local` (tools/dev.mjs): theme dev parte DOPO la prima build
npm run start:events # come start:watch, con l'inspector degli standard storefront events
npm run start:sync   # come start:watch, con --theme-editor-sync: le modifiche del theme editor finiscono nei JSON locali
npm run start:measure # come start:watch, ma build minificata e senza sourcemap (prima misura con Lighthouse da DevTools)
npm run shopify:push:dev   # build + push sul tema condiviso (ID in shopify.theme.toml)
npm run shopify:push:prod  # build + push in PRODUZIONE
```

Ambiente Windows con PowerShell 5.1: **non modificare file con `Get-Content`/`Set-Content`** (leggono UTF-8 come ANSI e corrompono le lettere accentate). Usa gli strumenti di edit, oppure .NET con `UTF8Encoding($false)` esplicito.

**Mai `sed -i` (o altri strumenti che creano file temporanei) nelle cartelle del tema** (`sections/`, `blocks/`, `snippets/`, `layout/`, `templates/`, `config/`, `locales/`): `sed -i` scrive un file temporaneo (es. `sections/sed0TfNHh`) accanto all'originale; se `shopify theme dev` è attivo lo carica, Shopify lo rifiuta ("Must have a .liquid file extension") e theme dev mostra "Failed to Upload Theme Files" al posto del negozio finché non viene riavviato (successo il 2026-11-03). Usa gli strumenti di edit o Node (`fs.writeFileSync`, scrittura diretta).

**Theme editor**: senza `start:sync` le modifiche fatte nell'editor del tema di sviluppo restano solo sul tema remoto e vengono sovrascritte al riavvio di theme dev. Con `start:sync` l'utente può avere modifiche non committate in `templates/*.json`, `sections/*-group.json` e `config/settings_data.json` arrivate dall'editor: non sono errori da annullare, e restano valide le regole su `settings_data.json`. Può riscrivere anche `locales/*.json`, con l'intestazione "auto-generated" (innocua, Theme Check la accetta, ma il file non si legge più con `JSON.parse`): il 2026-11-06 ha sovrascritto `en.json` subito dopo due edit ravvicinati e l'ultima chiave aggiunta è andata persa. Se è attiva, dopo aver aggiunto chiavi ricontrolla che ci siano ancora: `npm run lint` segnala quelle mancanti.

Non avviare `npm run watch` / `start:watch` / `start:events` / `start:sync` per verificare il lavoro: sono processi che non terminano. Il dev server Vite con HMR è stato rimosso di proposito (2026-11-03: funzionava solo sul browser locale e raddoppiava le modalità da mantenere): non reintrodurlo senza chiederlo all'utente.

**Sincronizzazione con lo store**: all'avvio `shopify theme dev` carica i file locali così come sono in quel momento; se Vite li sta ancora rigenerando, le modifiche vanno perse (tema remoto con asset/`vite-tag` vecchi). Per questo `start:watch`/`start:events` usano `tools/dev.mjs`, che avvia theme dev solo dopo la prima build. Se l'utente segnala che una funzionalità JS "non funziona" sullo store, prima di toccare il codice verifica con `shopify theme pull --only` (in una cartella temporanea) che asset e `vite-tag` remoti siano aggiornati.

**Entrypoint nuovi**: Vite fissa l'elenco di `frontend/entrypoints/` all'avvio. `npm run watch` (`tools/watch.mjs`) si riavvia da solo quando un entrypoint viene aggiunto/rimosso; `npm run lint` avvisa se un entrypoint manca in `vite-tag.liquid` (la section resterebbe senza JS/CSS: es. carrello senza `cart.js` → "Rimuovi" ricarica la pagina e riempie la cronologia). Se vedi quell'avviso, dillo all'utente: va riavviato il suo watch.

**Verifica = `npm run build:check` + `npm run lint`. Non usare `npm run build` per verificare**: svuota e rigenera `assets/`, e se l'utente ha `shopify theme dev` attivo la CLI cancella e ricarica gli asset sul tema remoto. Se theme dev viene fermato a metà, il tema resta senza CSS (è già successo il 2026-11-02). Usa `npm run build` solo quando serve davvero aggiornare `assets/` (es. prima di un push, che comunque la esegue da sé).

## Allineamento totale con Shopify (requisito dell'utente)

Il tema deve sfruttare **praticamente tutte** le funzionalità che Shopify offre agli storefront Liquid, con le API e i pattern ufficiali più recenti (ultima Shopify Edition + developer changelog). Prima di implementare o modificare qualsiasi funzionalità del negozio usa la skill **`shopify-alignment`**: verifica sulle fonti ufficiali (mai a memoria), implementa e aggiorna il registro [docs/shopify-alignment.md](docs/shopify-alignment.md).

Standard storefront events and actions (giugno 2026): helper in `frontend/scripts/standard-events.js` (`withCartEvent`, `withProductSelectEvent`, `<s-view-event>` + filtro `standard_event_data`, `configureStorefrontActions` registrata nel layout prima di `content_for_header`). Ogni nuova interazione commerciale emette il proprio evento `shopify:*`; ogni promise di evento si risolve o si rifiuta sempre; mai eventi cart dopo `Shopify.actions.updateCart`. Verifica con `npm run start:events` (watch + theme dev con `--standard-events-inspector`).

## Regole non negoziabili

- **Mai modificare `assets/` o `snippets/vite-tag.liquid`**: sono output generato (in `.gitignore`). Le sorgenti stanno in `frontend/`.
- **Mai eseguire push o comandi che scrivono sullo store** (`shopify theme push`, `shopify:push:*`, `shopify theme publish`, `delete`, `rename`) senza richiesta esplicita dell'utente nel messaggio corrente. Per la produzione chiedi sempre conferma.
  Questa regola è anche imposta tecnicamente in `.claude/settings.json`: push in produzione, `--live`/`--allow-live`, `publish`, `delete` e `rename` sono bloccati (regole `deny` + hook `PreToolUse`); il push sul tema di sviluppo richiede conferma. Se un comando viene bloccato, non cercare di aggirarlo: indica all'utente il comando da eseguire manualmente.
- **Mai modificare `config/settings_data.json`** salvo richiesta esplicita: contiene le personalizzazioni del merchant.
- **`shopify.theme.toml`**: l'ambiente `local` (senza theme ID) è per `theme dev`; `development` riceve solo build. Non puntare `theme dev` al tema condiviso.
- Prima di dichiarare un task completato: `npm run build:check` deve riuscire e `npm run lint` terminare senza **nuovi** errori. Se non hai verificato qualcosa (es. comportamento nel browser), dillo esplicitamente.

## Architettura

```
frontend/entrypoints/   ogni file = un bundle caricato con {% render 'vite-tag', entry: 'nome.js' %}
frontend/scripts/       moduli JS importati dagli entrypoint (o via dynamic import)
frontend/styles/        tokens.css (@theme Tailwind), base.css, utilities.css (@utility), componenti condivisi
frontend/assets/        font/immagini referenziati da CSS/JS (Vite li emette con hash)
frontend/public/        file copiati così come sono in assets/ (per asset_url nel Liquid)
layout/ sections/ snippets/ templates/ config/ locales/   file Liquid/JSON del tema
.claude/settings.json   permessi e hook di protezione per Claude Code (condivisi nel repo)
.claude/skills/         procedure ricorrenti (es. new-section)
```

- Alias import: `@/` e `~/` → `frontend/`.
- `assets/` su Shopify è piatta: niente sottocartelle nei nomi output.
- Il layout carica solo `theme.css` e `theme.js` (globali, da tenere minimi). Codice specifico va in entrypoint dedicati caricati dalla section/template che li usa, oppure in dynamic import da `theme.js`.

## Convenzioni Liquid

- Sintassi `{% render 'snippet', param: valore %}`; mai `include`. Parametri espliciti, niente variabili globali implicite negli snippet.
- Usa `{% liquid %}` per blocchi di logica con più `assign`/`if`.
- **Blocchi con soli spazi non vengono stampati**: per Liquid un `if`/`unless`/`for` il cui contenuto è solo whitespace è "blank" e non produce output (es. lo spazio tra parole in `{% unless forloop.last %} {% endunless %}` sparisce). Se serve stampare uno spazio usa un output esplicito: `{{ ' ' }}`.
- Testi visibili: niente stringhe hardcoded nei template destinati al merchant → setting della section (testi editabili) o `{{ 'chiave' | t }}` con chiavi in `locales/` (testi UI fissi).

## Traduzioni (italiano default + inglese)

- **Testi del negozio** (`| t`): ogni chiave va aggiunta sia in `locales/it.default.json` sia in `locales/en.json`, nello stesso task. Plurali con `zero`/`one`/`other` e `| t: count: …`.
- **Testi dell'editor** (schema di section e `settings_schema.json`): scrivi lo schema in italiano, poi lancia `npm run schema:i18n`. Lo script sostituisce i testi con chiavi `t:…`, li salva in `locales/it.default.schema.json` ed elenca le chiavi mancanti in `locales/en.schema.json`: aggiungile tradotte finché l'elenco è vuoto. Non scrivere a mano chiavi `t:` nuove senza passare dallo script.
- Theme Check segnala chiavi mancanti o non corrispondenti tra le lingue: `npm run lint` deve restare a 0 errori.
- Immagini: sempre `image_url` + `image_tag` con `widths`/`sizes` adeguati, `loading: 'lazy'` sotto la piega, `loading: 'eager'` + `fetchpriority: 'high'` per l'immagine LCP. Mai `img_url` (deprecato).
- Escape dell'output utente con `| escape` negli attributi; `| json` per passare dati a JS.
- Rendi le section compatibili con il theme editor: `{{ block.shopify_attributes }}` sui blocchi, nessuna dipendenza da stato JS globale non reinizializzabile.

## Convenzioni section (`{% schema %}`)

- `name` breve, `tag` e `class` se servono per lo styling, `settings` con `id` in snake_case e `label`/`info` chiari per il merchant.
- Usa `blocks` per contenuti ripetibili, `max_blocks` quando ha senso, `presets` per rendere la section aggiungibile dal theme editor.
- Ogni section con `presets` dichiara dove si può aggiungere (senza, Shopify la offre anche nei gruppi header/footer): contenuto → `"disabled_on": { "groups": ["header", "footer"] }`; header/footer → `"enabled_on": { "groups": ["header"] }` / `["footer"]`; `main-*` → `"enabled_on": { "templates": [...] }`.
- Header trasparente solo se `header` è l'ultima section del gruppo header (subito prima di `<main>`): una section messa dopo l'header lo fa restare pieno (condizione `body:has(> .section-header + main)` in `theme.css`/`header.css`). La barra annunci va sopra l'header.
- Larghezza: massimo da Impostazioni tema → Layout (`settings.layout_page_width`, token `--container-page`). Una section con griglie o immagini grandi aggiunge il setting `section_width` (`page`/`full`) come primo del pannello e `{% render 'section-width', section_id: section.id, width: section.settings.section_width %}` subito dopo `section-colors`: `page-width` e `max-w-page` si adattano da soli. Non cambia nulla sotto la larghezza massima, quindi su mobile testi e card tengono il margine; un'immagine grande può arrivare ai bordi con `-mx-(--page-gutter) lg:mx-0`. Niente `80rem` nei `sizes` (non accettano `var()`): si calcolano da `settings.layout_page_width`, o da `100vw` se `full`. Formati più grandi solo se `full` (`image_max`/`image_widths`, parametro `full_width` delle card): `image_tag` e `image_url` vanno alzati insieme, e su "Pagina" restano fuori per non pesare sugli schermi ad alta densità. Non lo hanno le section di lettura (articolo, pagina, FAQ, form, carrello) né quelle già da bordo a bordo (`gallery`, `scroll-gallery`; `carousel` e `ticker` hanno la loro opzione per la striscia, con titolo e misure allineati alla pagina).
- Default sensati in ogni setting: la section appena aggiunta deve avere un aspetto accettabile.
- Per creare una nuova section segui la skill `new-section` (`.claude/skills/new-section/SKILL.md`).

## Convenzioni JavaScript

- ES modules, niente jQuery né librerie pesanti senza motivo. Valuta sempre il peso nel bundle (`npm run build:check` mostra le dimensioni gzip).
- Componenti interattivi come **custom elements** (`class ProductForm extends HTMLElement`, registrati con `customElements.define` protetto da `if (!customElements.get(...))`): si inizializzano da soli anche quando il theme editor ricarica una section.
- Codice pesante o non usato ovunque → dynamic import condizionale (vedi `loadAnimations` in `frontend/entrypoints/theme.js`).
- Varianti di una section scelte da un setting (es. le disposizioni di `gallery`): una variante per entrypoint, importata in modo dinamico dal componente con percorsi letterali, e la section stampa anche il `vite-tag` della sola variante scelta (si scarica in parallelo, l'import non aggiunge richieste; nel theme editor l'import copre il cambio di setting). Il componente si mostra pronto con un attributo (`data-ready`), non con `:defined`.
- Eventi theme editor da gestire quando serve: `shopify:section:load`, `shopify:section:unload`, `shopify:block:select`.
- Niente `console.log` lasciati nel codice finale.

## Design system (Simple Design System → Tailwind CSS v4)

Fonte: file Figma "Simple Design System" dell'utente, `https://www.figma.com/design/HReSVIoQDNA6ZLlMs6Biho` (pagina Foundations per i token, pagine componente per Accordion, Tabs, Buttons, Cards…). Da Figma si prendono **token e layout**, mai icone o asset (vedi Icone).

- **Token** solo in `frontend/styles/tokens.css` (`@theme static`), con il nome SDS originale in commento:
  - colori semantici: `background`, `surface`, `surface-hover`, `foreground`, `muted`, `subtle`, `border`, `border-strong`, `primary`(`-hover`, `-foreground`), `neutral`(`-muted`, `-subtle`, `-surface`), `positive|warning|danger`(`-surface`, `-foreground`), `overlay`. Palette Tailwind rimossa → mai hex.
  - colori dal merchant: `color_palette` (Impostazioni tema → Colori, stampata da `snippets/head-styles.liquid`) dà `background`, `foreground`, `primary`, `primary-foreground`; tutti gli altri token si ricavano da questi con `color-mix` (blocco `:root, .shopify-section:has(> style[data-shopify])` in `tokens.css`). Niente schemi di colore (scelta dell'utente del 2026-11-05, vedi `docs/shopify-alignment.md`). Colori di una section: setting `color_background`/`color_text` + `{% render 'section-colors', … %}` come primo elemento del file, fuori da ogni elemento e condizione (ogni nuova section con contenuti lo aggiunge). Sopra foto e video i colori sono fissi (`text-white`, `text-black`, `button-inverse`, `button-glass`), mai `text-foreground`: con una palette scura sarebbe chiaro su velo bianco.
  - tipografia SDS (scala Tailwind sostituita): `text-title-hero`, `text-title-page`, `text-subtitle`, `text-heading`, `text-subheading`, `text-body`, `text-body-sm`, `text-code` (dimensione, interlinea, tracking e peso inclusi). Font: `font-sans` / `font-heading` dalle impostazioni tema (`snippets/theme-fonts.liquid`, default Inter).
  - spaziature: scala Tailwind standard (coincide con SDS: `p-1`=4px, `p-2`=8, `p-3`=12, `p-4`=16, `p-6`=24, `p-8`=32, `p-16`=64…).
  - raggi `rounded-sm|md|lg|xl` (4/8/16/24), ombre `shadow-100…600`, breakpoint `md` = 750px, `lg` = 990px, `max-w-page`.
- **Componenti base** (`frontend/styles/components.css`, `@utility`): `button` + varianti `button-primary|button-neutral|button-subtle`, taglie `button-sm` (36px) / default (44px) / `button-lg` (52px, azione principale della pagina: hero, aggiungi al carrello, checkout), `button-icon` per i pulsanti solo icona (mai `rounded-full` a mano); sopra immagini/video scuri `button-inverse` e `button-glass` (sempre con `focus-visible:outline-white`). Taglie e varianti impostano solo variabili `--button-*`. Forma da Impostazioni tema → Pulsanti: per controlli simili ai pulsanti (chip delle varianti, selettore quantità, voci del menu) usa `rounded-button`. I pulsanti di pagamento rapido seguono forma e altezza tramite le variabili `--shopify-accelerated-checkout-*`; `prose prose-theme` per i contenuti richtext del merchant (utility del tema in `frontend/styles/prose.css`, non il plugin `@tailwindcss/typography`, rimosso per alleggerire il CSS globale: varianti disponibili `prose-p:`, `prose-ul:`, `prose-ol:`, `prose-li:`, `prose-headings:`, `prose-a:`). Easing del tema: utility `ease-theme` (token `--ease-theme`). Altezza dell'header in `--header-height` (misurata da `header.js`).
- **Riscontri e controlli piccoli**: casella = `<input class="peer checkbox">` + icona `check` con `check-tick` in un contenitore `relative size-5` (mai `accent-*`, mai la spunta a mano). Tooltip = `<span class="tooltip" aria-hidden="true">` dentro un genitore `relative` che ha già quel testo come nome accessibile (`tooltip-below` per ciò che sta in cima allo schermo); mai dentro contenitori che tagliano o scorrono. Toast = `showToast(messaggio, { tone, action })` da `frontend/scripts/toast.js`, solo per esiti senza un posto vicino: gli errori di un campo o di una riga restano lì. Dentro un `<dialog>` modale si inserisce da solo nel dialog (fuori sarebbe inerte).
- **Stati di caricamento per tipo di contenuto** (`frontend/styles/loading.css`, `frontend/scripts/loading-states.js`): contenitore di un'immagine → `media-loading` (posizionato e con `overflow-hidden`: riflesso dietro l'immagine, che non viene mai nascosta, quindi nessun ritardo per l'LCP); testi e card in arrivo → `skeleton` (mai `animate-pulse`); azione → `aria-busy="true"` su un `button` (tre puntini al posto dell'etichetta, che resta per i lettori di schermo); pagina → barra in alto se tarda più di 200ms (Navigation API, Impostazioni tema → Transizioni tra pagine); risultati che si aggiornano → `aria-busy` + opacità, spinner nel campo di ricerca.
- **Snippet condivisi**: `section-header` (titolo + intro standard delle section), `product-card` (card unica per tutte le section: aspetto da Impostazioni tema → Card prodotto, seconda immagine all'hover, selettore colore con `frontend/scripts/product-card.js` + `sections/product-card.liquid`; layout `grid` o `fill`), `price` (prezzo prodotto/variante, scontato, "a partire da", prezzo unitario), `accordion-item` (righe con filetto come i filtri, non la card del SDS; dentro `<accordion-group>`, che se ha un `gap` lo dichiara anche in `--accordion-gap`; JS in `frontend/entrypoints/accordion.js`, CSS in `frontend/styles/accordion.css` dentro theme.css: FAQ, pannelli prodotto), `icon`; prodotto: `product-variant-picker`, `product-quantity`, `product-buy-buttons` (pagina prodotto e anteprima rapida, JS in `frontend/scripts/product-page.js`); `quick-view` (anteprima rapida: dialog + `quick-view.js`, contenuto da `sections/quick-view.liquid` via Section Rendering API; trigger con `show({ url, origin, label })`; sotto i 750px pannello dal basso che scorre tutto insieme, con il pulsante del carrello sempre in vista: `sticky_actions` di `product-buy-buttons`, che rende il form `display: contents` perché uno sticky non esce dal suo genitore).

## Qualità visiva (requisito su ogni task)

Il tema è un prodotto da vetrina: ogni modifica, anche solo tecnica (carrello, varianti, template), deve uscire curata come se la firmasse un UI designer. Funzionare non basta.

- **Stati completi** per ogni elemento interattivo: hover, `focus-visible` (contrasto adeguato anche su sfondi scuri o su immagini), active/pressed, disabled, caricamento, vuoto, errore. Un componente senza stato vuoto o di caricamento non è finito.
- **Gerarchia e ritmo**: solo token SDS per tipografia, colori, spaziature, raggi e ombre. Spaziature verticali coerenti tra le section (`py-8 md:py-16` come base, `py-12 md:py-24` per le section di apertura: sotto i 750px due section vicine sommano il padding, e con 48px per lato erano 96px di vuoto su uno schermo da 667), `text-balance` sui titoli e `text-pretty` sui paragrafi, misura del testo limitata (`max-w-2xl` circa per i paragrafi).
- **Responsive progettato**, non adattato: mobile-first, verificato a 375, 750 e 990px e su schermi larghi (`max-w-page`). Unità `svh`/`dvh` per le altezze legate allo schermo, mai `vh`. Niente testo sopra un'immagine senza un overlay che garantisca il contrasto.
- **Movimento con uno scopo**: dare un riscontro, guidare lo sguardo, comunicare un cambio di stato. Easing di riferimento `[0.22, 1, 0.36, 1]` (ease-out del tema), 150-250ms per le micro-interazioni, 400-700ms per gli ingressi, molle per ciò che si trascina o si apre (senza rimbalzo, `bounce: 0`, per pannelli e modali che cambiano molto di dimensione: anche un rimbalzo piccolo li fa crescere oltre la misura finale e poi rimpicciolire, e si legge come uno scatto). Animazioni guidate dallo scroll con `scroll()` di Motion collegato a un'animazione (timeline nativa, fuori dal main thread) invece di callback per frame quando possibile. Sempre `prefers-reduced-motion` e mai a scapito di LCP/CLS/INP.
- **Tailwind idiomatico**: varianti prima del CSS custom (`group-*`, `peer-*`, `has-*`, `aria-*`, `data-*`, `open:`, `starting:`, `motion-safe:`); valori dal merchant via variabili CSS (`style="--x: …"` + `utility-(--x)`).
- **Occhio critico**: se nei file toccati noti difetti visivi o di UX (contrasto, allineamenti, stati mancanti, salti di layout), segnalali all'utente con una proposta concreta anche se non fanno parte della richiesta.

## Convenzioni CSS (Tailwind CSS v4)

- **Utility-first nel Liquid** per layout, spaziature, tipografia, colori, stati (`hover:`, `focus-visible:`, `open:`, `aria-selected:`, `group-*`, `md:`). Mobile-first. Per classi lunghe ripetute nello stesso file usa `{% capture %}`.
- **Varianti custom** (definite in `theme.css`): `js:` = solo con JS attivo (es. `hidden js:flex`); `js-motion:` = JS attivo e movimento non ridotto, cioè le modalità animate (es. `js-motion:sticky`, `md:js-motion:…`). Devono restare allineate alle media query usate nei JS delle section.
- **Header trasparente**: varianti `overlay:` / `overlay-light:` (header sopra la prima section, finché non torna pieno con `data-solid`) e `under-header:` (contenuto della prima section che sta sotto l'header). Una section consente l'header trasparente con `data-header-overlay="light|dark"` (oggi: hero a tutta larghezza con media). Tutto CSS con `:has()`: niente salti al primo rendering. Una nuova section "a tutto schermo" che lo vuole deve marcarsi così e usare `under-header:` per lo spazio in alto.
- **CSS della section** (`frontend/entrypoints/<section>.css`) solo come ultima risorsa: stati prima della definizione del custom element (`:not(:defined)`), stati `[data-state]` legati al JS, variabili CSS calcolate. Sempre dentro `@layer components { … }` (le utility vincono sempre sui components: non usare il CSS per sovrascrivere una utility, usa una variante). Se non serve, niente file CSS e niente `vite-tag` CSS nella section.
- **Classi dinamiche**: Tailwind legge i file sorgente, non il Liquid renderizzato. Mai comporre nomi di classe (`lg:grid-cols-{{ columns }}` non funziona): usa un `case` con classi complete oppure una variabile CSS (`style="--columns: {{ columns }}"` + `lg:grid-cols-[repeat(var(--columns),minmax(0,1fr))]`). Attenzione: `grid-cols-(--x)` genera `grid-template-columns: var(--x)`, valido solo se la variabile contiene già un elenco di tracce (es. `repeat(4, …)`); con un numero il valore non è valido e la griglia resta a una colonna (successo il 2026-11-04 nella pagina collezione). Stesso discorso per le altre utility che si aspettano un elenco di tracce o una funzione.
- `@source` in `frontend/entrypoints/theme.css` elenca dove Tailwind cerca le classi (layout, sections, snippets, templates, JS in `frontend/`). Se aggiungi una nuova cartella con markup (es. `blocks/`), aggiungila lì. **Mai includere file generati dalla build** (`snippets/vite-tag.liquid` è escluso con `@source not`; `assets/` non va mai in `@source`): in `npm run watch` ogni build ne avvierebbe un'altra all'infinito. Per lo stesso motivo `build.watch.exclude` in `vite.config.js` ignora `assets/`, `vite-tag.liquid` e `.build-check/`. Nel watch `assets/` non viene svuotata: i file con hash non più prodotti li elimina dopo ogni build il plugin `tools/prune-stale-assets.mjs` (theme dev li toglie anche dal tema remoto).
- Utility custom con `@utility` in `frontend/styles/utilities.css` (es. `page-width`). Per testo nascosto usa `sr-only`.
- Il reset è il Preflight di Tailwind (liste senza puntini, titoli senza dimensioni): i contenuti `richtext` del merchant vanno sempre in un contenitore `prose prose-theme max-w-none`.
- Rispetta `prefers-reduced-motion` per qualsiasi animazione o transizione significativa (`motion-safe:` / `motion-reduce:`).

## Animazioni (Motion)

- Usa il sistema dichiarativo esistente: `data-animate="fade-up"`, `data-animate-stagger="…"` (preset in `frontend/scripts/animations.js`, stato iniziale in `frontend/styles/animations.css`).
- **Mai** `data-animate` su elementi above-the-fold o sull'elemento LCP.
- **Anteprima dei preset** (selettore "Aggiungi section"): se tutto il contenuto di una section è dentro `data-animate-stagger`, parte nascosto e l'editor mostra "No preview available" (misurato il 2026-11-06, non documentato). Nella section: `{% unless section.index == 1 or request.visual_preview_mode %}` attorno all'attributo. La correzione va nella section, non nel layout: nell'anteprima il flag è vero nella section, ma un attributo stampato con lo stesso flag nel layout non arriva su `<html>`. `request.design_mode` è vero anche lì, quindi i segnaposto non richiedono altro.
- Altezze animate (accordion, pannelli che si espandono): il contenitore ha `overflow: hidden` durante l'animazione, quindi **niente margini negativi né traslazioni verso l'esterno** sul contenuto: verrebbe tagliato (es. prima riga "a strisce" nella FAQ). Distribuisci le distanze con il padding.
- Per animazioni custom preferisci `import { animate } from 'motion/mini'`; il pacchetto completo `motion` solo se servono spring, scroll-linked o sequenze.
- **Scorrimento morbido** (Lenis, `frontend/scripts/smooth-scroll.js`, Impostazioni tema → Scorrimento): solo rotella/trackpad, guidato dal frame loop di Motion. Si ferma da solo quando `<html>` ha `overflow: hidden` (dialog, menu mobile) e lascia scorrere in modo nativo i contenitori interni. `autoToggle` mette su `<html>` una transizione di 1ms su `overflow`: il blocco arriva 2 o più fotogrammi dopo, quindi ciò che deve cambiare insieme alla barra di scorrimento passa dalla stessa transizione (`transition-property` in `frontend/styles/scroll-lock.css`: il padding che compensa la barra, misurato il 2026-11-05). Un nuovo pannello/overlay che blocca la pagina prende l'attributo `data-scroll-lock` (`<dialog>`/`<details>`): blocco, compensazione della barra (`--scrollbar-width`, `frontend/scripts/scrollbar-width.js`) e sincronia con Lenis sono in quel file, niente `overflow: hidden` né classi a mano. Un contenitore che deve restare nativo in ogni caso prende `data-lenis-prevent`. Per scrollare da JS usa `scrollTo`/`scrollIntoView` nativi (Lenis li segue).
- **Transizioni tra pagine** (Impostazioni tema → Transizioni tra pagine): View Transitions native tra documenti, niente librerie né navigazione "SPA" simulata (romperebbe app, analytics e standard events). Attivazione e script `pageswap`/`pagereveal` in `snippets/page-transitions.liquid` (deve restare uno script classico nel `<head>`), effetti in `frontend/entrypoints/page-transitions.css` (CSS a parte, caricato dallo snippet nel `<head>` solo con le transizioni attive: non rimetterlo in `theme.css`). I `view-transition-name` si assegnano solo durante la transizione (mai fissi nel CSS) e devono essere unici nella pagina. Immagine condivisa: card `[data-card-media]` / anteprima rapida `[data-quick-view-media]` ↔ `#ProductMediaMain` in `main-product` (non con pixel e tendina a fasce). Il bfcache ripristina una pagina con il `<dialog>` ancora aperto: al ritorno `pagereveal` guarda `dialog:modal` e la foto atterra nell'anteprima, non sulla card sotto il velo. Pixel e tendina a fasce: tessere temporanee create in `pagereveal` (`view-transition-class: page-tile`), codice stampato solo se l'effetto (o "Mista") lo usa. `scale`/`rotate`/`translate` vanno su `::view-transition-new|old(…)`, **mai sul `::view-transition-group`**: il gruppo nasce in alto a sinistra ed è portato al suo posto dal browser con `transform`, e le proprietà individuali si applicano dopo, attorno a quell'angolo (le tessere "volavano" da e verso l'alto a sinistra, corretto il 2026-11-04). **Mai `clip-path` nei keyframe delle rivelazioni**: con il main thread occupato Chrome può disegnare, alla chiusura della transizione, un fotogramma con un ritaglio vecchio: la tendina ricompare a transizione finita (misurato il 2026-11-05 su 30 navigazioni: 2-4 flash con wipe, clip_wipe, doors e iris; 0 con il flag che toglie il clip-path dal compositor; la causa precisa è dedotta da queste misure, non documentata). Si scrive `clip-path` con `calc(var(--page-transition-progress) …)` e si anima la proprietà registrata, come per le maschere. Immagine condivisa: la foto di partenza resta piena per tutto il volo e l'arrivo le compare sopra; se l'immagine non è ancora caricata, lo script mette in pausa l'animazione d'arrivo (al massimo 1,5 s). Un `<link rel="expect">` si sblocca appena l'elemento compare, non quando è completo: per aspettare tutto `<main>` serve `#MainEnd` nel layout, usato solo al ritorno sulla card. Lo script inline non passa da Theme Check né da Vite: dopo ogni modifica controllane la sintassi (es. estrarlo e `node --check`).
- Prima di creare una section animata consulta [docs/motion-examples.md](docs/motion-examples.md): elenca gli esempi Motion con codice gratuito riutilizzabile, quelli solo Motion+ (da non copiare) e lo stato delle section già create. Aggiorna la colonna "Stato" quando ne completi una.

## SEO, accessibilità e performance (requisito su ogni task)

Il tema deve superare al meglio Lighthouse / PageSpeed Insights (Performance, Accessibilità, Best practice, SEO), axe e le linee guida di Google: ogni modifica rispetta queste regole, non solo gli audit. Per una verifica completa usa la skill `theme-review`.

**Accessibilità (WCAG 2.2 AA)**
- HTML semantico, un solo `h1` per pagina, gerarchia dei titoli senza salti; landmark (`header`, `nav` con `aria-label` se più di una, `main`, `footer`).
- Elementi interattivi raggiungibili e utilizzabili da tastiera con focus visibile; `button` per azioni, `a` per navigazione; mai elementi interattivi annidati (es. un `<a>` dentro un `role="option"`: il ruolo va sul link).
- Nome accessibile per ogni controllo (pulsanti solo icona con `sr-only`/`aria-label`, campi con `label`); attributi ARIA solo se l'HTML nativo non basta.
- **Contrasto** (dai token reali): testo ≥ 4.5:1, testo grande e bordi dei controlli ≥ 3:1. Combinazioni da evitare: `text-muted` su `bg-surface` (4.8:1 con la palette predefinita, ma 4.3:1 su fondi colorati → usa `text-foreground/80`), `text-subtle` per testo leggibile (2.1:1: solo icone decorative o elementi disabilitati), `border-border` come unico contorno di un campo (1.4:1 → campi, select e textarea con `border-border-strong`). Testo su immagini sempre con overlay o velo sufficiente.
- Dopo un aggiornamento del DOM (Section Rendering, carrello, filtri) il focus non deve perdersi: id stabili sui controlli e ripristino del focus, regioni `aria-live` per annunciare il risultato.
- Contenitori scorrevoli senza elementi focusabili: attributo `data-scroll-region` + `aria-label` (diventano focusabili solo quando scorrono, `frontend/scripts/scroll-regions.js`).
- `alt` sulle immagini (da `image.alt` con fallback sensato, decorative con `alt=""`); movimento sempre con `prefers-reduced-motion`; contenuti in movimento automatico con pausa (WCAG 2.2.2).

**SEO**
- Il `<head>` (layout + `snippets/meta-tags.liquid`) gestisce titolo, meta description, canonical, Open Graph/Twitter e favicon: non duplicarli nelle section.
- Mai contenuti segnaposto (prodotti finti, link `#`, prezzi di esempio) nel negozio pubblicato: solo con `request.design_mode`.
- Link con testo descrittivo (o completato da `sr-only`), mai link a sé stessi come ripiego: se manca l'URL il pulsante non si mostra.
- Dati strutturati con i filtri Shopify (`structured_data`) o JSON-LD con `| json`; URL sempre da `routes.*`.

**Performance (Core Web Vitals)**
- LCP: la prima immagine visibile (prima section: `section.index == 1`) con `loading: 'eager'` + `fetchpriority: 'high'`, mai nascosta da animazioni; tutte le altre `lazy`. `widths`/`sizes` realistici.
- Mai `scroll-padding` su `<html>`/`body`: le scroll timeline native (Motion `scroll(animation)`) lo sottraggono dall'area visibile e le animazioni partono già avanzate (successo il 2026-11-04: immagine della hero spostata in basso). Per l'header fisso usare `scroll-margin-top` sugli elementi raggiunti (`header.css`).
- CLS: dimensioni sempre note (`image_tag` le mette), stati prima del JS gestiti in CSS, niente contenuto inserito sopra il fold dopo il caricamento.
- INP: niente lavoro pesante all'avvio, JS per pagina in entrypoint dedicati o import dinamici, animazioni sul compositor (`transform`/`opacity`, timeline di scroll native).
- CSS globale (`theme.css`) e JS globale (`theme.js`) restano piccoli: soglia **~18 KiB in Brotli** per il CSS (decisa con l'utente il 2026-11-06, quando era a 17,35 KiB; misure in [docs/roadmap.md](docs/roadmap.md)). Superarla segnala una regressione da guardare. La build non mostra il Brotli: si misura con `zlib.brotliCompressSync` di Node sul file di `.build-check/`. I kB di Vite sono in base 1000 (quel giorno 129,97 kB, 22,09 kB gzip): non confrontarli con misure in base 1024. Non dividere le utility Tailwind in più fogli: una `.hidden` del secondo foglio batterebbe una `md:flex` del primo, e simulando la divisione la home peggiora comunque. Fuori da `theme.css` va il CSS di componente specifico di una pagina, in un entrypoint dedicato (`collection.css`, `page-transitions.css`).
- **Misurare sulla build di produzione**: Lighthouse su `theme dev` con il watch (non minificato, sourcemap inline) dà numeri molto peggiori del reale. Si misura sul tema di sviluppo caricato con `npm run shopify:push:dev` (fa `npm run build`).
